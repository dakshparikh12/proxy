## 1. `settings.py` — Fail-fast boot gate

### What it does
Validates every required secret/config key at import time using pydantic-settings. Crashes naming the missing key rather than failing on first use.

### Test items

[CAPABILITY] `load_settings()` returns a populated `Settings` object when all required env vars are present.

[CAPABILITY] `_is_prod()` returns True when `PROXY_ENV` is `prod` or `production` (case-insensitive, stripped), False for `local`/`staging`/unset.

[CAPABILITY] `Settings.anthropic_auth_configured()` returns True when any of the four auth modes is set: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_USE_VERTEX`, or `CLAUDE_CODE_OAUTH_TOKEN`.

[CAPABILITY] `Settings.resolved_recall_webhook_secret()` returns canonical `RECALL_WEBHOOK_SECRET` when set; falls back to legacy `RECALL_WORKSPACE_VERIFICATION_SECRET` when only that is set.

[WIRING] `settings` module-level singleton is instantiated at import time — any consumer importing `settings` triggers the boot gate immediately (not lazily on first field access).

[FAILURE] Missing `DATABASE_URL` → RuntimeError at import naming "DATABASE_URL". Must not silently proceed.

[FAILURE] Missing `GCS_BUCKET`, `RECALL_API_KEY`, `AES_KEY_RECALL`, `AES_KEY_STT`, `AES_KEY_CALENDAR`, or no Anthropic auth mode → RuntimeError naming the specific missing key.

[FAILURE] In prod, missing `SESSION_SECRET` → boot crash naming the key (prevents session forgery).

[FAILURE] In prod, missing `PUBLIC_BASE_URL` → boot crash (silent dead deployment risk: relay URL and draft approve links can't be built).

[FAILURE] In prod, missing any of `SESSION_SIGNING_KEY`, `INTERNAL_RECONCILE_TOKEN`, `PROXY_INTERNAL_TOKEN` → boot crash naming the key (prevents bearer token forgery).

[FAILURE] In prod, missing `GCP_PROJECT_ID` → boot crash.

[NUANCE] `RECALL_WEBHOOK_SECRET` and `RECALL_WORKSPACE_VERIFICATION_SECRET` are NOT boot hard gates: an unset value means the webhook route fails CLOSED (401) without crashing boot — so a deploy without inbound Recall webhooks still boots.

[NUANCE] `GITHUB_WEBHOOK_SECRET` is not a boot hard gate either — unset causes the GitHub webhook route to fail CLOSED (401) on every delivery.

[NUANCE] `SESSION_SECRET` is prod-gated not unconditional: a local run without it is accepted (dev fallback string); a prod run without it MUST crash.

[NUANCE] `_is_prod()` checks both `PROXY_ENV` and `ENVIRONMENT` (in that order) — a deployment using the legacy `ENVIRONMENT` key must still get the prod gate.

[EDGE] Multiple missing keys: all missing keys must be named in one RuntimeError message (not just the first).

[EDGE] Empty-string values for unconditional hard gates (e.g. `DATABASE_URL=""`) must still trigger the crash (not just None).

## 2. `app.py` — ASGI app factory and auth routes

### What it does
Assembles the FastAPI app: installs session middleware, safe-error handler, mounts all routes (meeting home, webhooks, gateway, connect, relay, meetings, accept/reject, output media), and registers the three Google OIDC auth routes + /health.

### Test items

[CAPABILITY] `GET /health` → `{"status": "healthy"}` at HTTP 200 regardless of auth.

[CAPABILITY] `GET /auth/login` → redirects to Google OIDC authorization endpoint (Authlib `authorize_redirect`).

[CAPABILITY] `GET /auth/callback` — on successful Google token exchange: creates/loads the durable `sessions` row via `complete_signin`, sets the `session` HMAC-signed cookie (`httponly=True, samesite='lax'`), and redirects to `/`.

[CAPABILITY] `GET /auth/logout` — deletes the durable `sessions` row (`logout_session`), clears the `session` cookie, redirects to `/`.

[WIRING] `/auth/callback` reads `email` from `token["userinfo"]` — if `userinfo` is missing/None, no `complete_signin` is called and no cookie is set (silent no-session degrade).

[WIRING] `app.state.db` must be populated before auth routes execute (set by server startup); if absent, `auth_callback` skips `complete_signin` silently.

[WIRING] `_resolve_session_from_request` — resolves the durable session first (DB lookup), falls back to Starlette `request.session["user"]` for back-compat. If DB is unavailable, falls back, not errors.

[WIRING] `_stamp_internal_scoped` stamps all `/internal/*` routes at app construction so the route-enumeration test can classify them as scoped (not raw).

[WIRING] Output-media routes from `in_meeting.output_media.router` are materialized directly into `app.router.routes` (not `include_router`) to avoid `_IncludedRouter` markers that the enumeration gate cannot classify.

[FAILURE] Google OIDC exchange fails (bad `code`, expired state) → `auth_callback` raises; safeError handler must NOT leak internals to caller (collapses to generic error).

[FAILURE] `SessionMiddleware` dep absent → `_install_signed_session` silently skips (no crash); session cookie is unsigned — caller gets None from `_resolve_session_from_request` via the `AssertionError/AttributeError` guard.

[FAILURE] `resolve_session` raises inside `_resolve_session_from_request` → caught by `except Exception` → falls back to middleware check, never propagates.

[NUANCE] `auth_callback` deliberately does NOT write to `request.session["user"]` (which would emit a colliding `Set-Cookie: session=` that clobbers the durable HMAC cookie — only one cookie, one source of truth).

[NUANCE] `protected()` dependencies on `install_accept_route` and `install_reject_route` use SEPARATE instances so each route's dependency tree is independently stamped for the enumeration test.

[NUANCE] Session cookie attributes: `httponly=True, samesite='lax'` — NOT `secure` (left to the deployment's TLS termination at Cloud Run level).

[EDGE] A non-existent/never-set `app.state.db` must not crash auth routes — handled by `getattr(request.app.state, "db", None)` null-check pattern.

[EDGE] Route enumeration: every non-public route must be stamped with `protected()` or `mark_internal_scoped`; the route-enumeration test catches any unwrapped endpoint.

## 3. `session.py` — HMAC-signed session cookie over DB rows

### What it does
Signs session IDs with HMAC-SHA256, stores them in a `sessions` Postgres table, and resolves them back to `{user_id, tenant_id}`.

### Test items

[CAPABILITY] `complete_signin(db, email=...)` → upserts `users` row, creates `sessions` row, returns `SignInResult` with HMAC-signed cookie and `user_id`/`tenant_id`.

[CAPABILITY] `resolve_session(db, cookies)` → verifies cookie HMAC, looks up `sessions` row, returns `{user_id, tenant_id}` or `None`.

[CAPABILITY] `logout_session(db, cookies)` → verifies cookie, deletes `sessions` row. Subsequent `resolve_session` with same cookie → None.

[WIRING] `complete_signin` uses `repos.identity.upsert_user_by_email` and `repos.sessions.create_session` — both must run on the same acquired connection.

[FAILURE] Tampered cookie (wrong MAC) → `_verify` returns None → `resolve_session` returns None (fails closed, never resolves the session).

[FAILURE] Malformed cookie (no `.` separator) → `_verify` returns None immediately.

[FAILURE] Valid HMAC but non-UUID session_id string → `uuid.UUID(session_id)` raises ValueError → `_cookie_session_uuid` returns None.

[FAILURE] Valid signed cookie but `sessions` row deleted (expired/logged out) → `get_session` returns None → `resolve_session` returns None (the DB row IS the source of truth).

[FAILURE] DB unavailable during `resolve_session` → exception propagates to `_resolve_session_from_request` which catches it and returns None (fail-closed).

[NUANCE] `_signing_key()` uses `SESSION_SIGNING_KEY` env var; falls back to `b"dev-insecure-session-key"` in non-prod. The prod boot gate ensures this literal CANNOT reach production.

[NUANCE] `hmac.compare_digest` used in `_verify` to prevent timing attacks on cookie verification.

[NUANCE] `_sign` uses `hmac.new` (not `hmac.new`) — the format is `{session_id}.{hex_mac}`.

[NUANCE] Both `complete_signin` and `resolve_session` must work with the SAME cookie name `session` used by both the Starlette middleware and the durable session mechanism — they cannot collide.

[EDGE] Same email signed in twice → `upsert_user_by_email` is idempotent, returns the same user. Each sign-in mints a NEW `sessions` row (not idempotent on sessions).

[EDGE] `logout_session` with a missing or invalid cookie → `_cookie_session_uuid` returns None → method is a no-op (never raises).

## 4. `connect.py` — Connect page routes and pre-meeting trigger

### What it does
Owns `POST /connect/install/start` (registers a fresh install + fires the background map-build trigger) and `GET /connect/status` (durable Postgres-backed readiness poll). `ConnectStore` is the durable substrate (psycopg, autocommit). `trigger_connect_index` drives `premeeting.run_pipeline` on a background daemon thread.

### Test items

[CAPABILITY] `POST /connect/install/start` with valid `repo_url` body → returns `{install_id, install_url}` at HTTP 200 immediately (background trigger spawned).

[CAPABILITY] `GET /connect/status?install_id=<id>` by the owning tenant → returns `{install_id, status, coverage_pct, gaps, flagged_files}` at HTTP 200.

[CAPABILITY] `ConnectStore.new_install` → creates `tenants` row (idempotent) then `connect_readiness` row at state `connecting`; returns opaque UUID hex install_id.

[CAPABILITY] `ConnectStore.mark_state` advances install to one of `{connecting, cloning, indexing, ready, not_ready}`; rejects any invalid state string before touching the DB row.

[CAPABILITY] `ConnectStore.set_ready` → writes terminal `ready` with real coverage_pct and flagged files array.

[CAPABILITY] `ConnectStore.set_not_ready` → writes terminal `not_ready` with named gaps list (never empty/fabricated).

[CAPABILITY] `ConnectStore.status` → reads `connect_readiness` row; unknown install → returns `ReadinessReport(status="connecting")` (never leaks whether install exists).

[CAPABILITY] `ConnectStore.tenant_for_install` → returns tenant_id for a known install, None for unknown.

[CAPABILITY] `_tenant_for_install(repo_url, installation_account=<account>)` → deterministic UUID5 keyed on account+repo; same inputs always yield same tenant.

[CAPABILITY] `_tenant_for_install(repo_url, installation_account=None)` → returns fresh UUID4 (random, never the repo URL — two anonymous connects of the same repo never collide).

[CAPABILITY] `github_app_install_url(repo_url)` → builds the correct GitHub App install URL using `PROXY_GITHUB_APP_SLUG` env var (default `"proxy"`).

[CAPABILITY] `_StoreReadinessListener.emit` → forwards `connecting`/`cloning`/`indexing` states to the store; skips `ready`/`not_ready` (terminal writes are done separately with their payload).

[WIRING] `trigger_connect_index` → spawned in a background daemon thread via `_spawn_trigger`; the route returns 200 before the trigger completes.

[WIRING] `trigger_connect_index` calls `asyncio.run(_run_pipeline_and_bind(...))` on the daemon thread (its own loop, never the main app loop).

[WIRING] `_run_pipeline_and_bind` opens a loop-local `Database` when the injected `map_store` carries a real async pool (cross-loop asyncpg fix), closes it in the `finally` block.

[WIRING] `_bind_repo_row_async` upserts the `repos` row for the tenant AFTER a clean `run_pipeline` result — this makes the repo findable for `POST /meetings`.

[WIRING] `GET /connect/status` resolves the caller's session FIRST (B7), then reads `tenant_for_install`, refuses (404) when the caller's tenant doesn't match the install's tenant.

[WIRING] `connect_status` and `connect_install_start` resolve the `ConnectStore` per-request off `request.app.state` (not a mount-time closure capture) so the durable handle is always current.

[FAILURE] `ConnectStoreUnavailable` during `new_install` → route returns 503 `{"error": "readiness substrate unavailable; try again shortly"}` — NOT a crash or 500.

[FAILURE] `ConnectStoreUnavailable` during `status` read → returns HTTP 503 with `not_ready` body explicitly naming the gap; NEVER returns a fabricated `ready`.

[FAILURE] `ConnectStoreUnavailable` during `tenant_for_install` → same 503 honest degrade.

[FAILURE] `trigger_connect_index` with `map_provider=None` → immediately records `connecting` then `not_ready` naming "map-build skipped: no model provider (D-032, unfunded key)"; NEVER fabricates a map.

[FAILURE] `run_pipeline` raises inside `_run_pipeline_and_bind` → `except Exception` catches → records `not_ready` naming the exception type; then re-raises (caught by `_spawn_trigger`'s outer except).

[FAILURE] `ConnectStoreUnavailable` inside `_StoreReadinessListener.emit` → silently suppressed (pipeline continues; terminal write reconciles).

[FAILURE] Postgres connection factory failure → `ConnectStore._conn` raises `ConnectStoreUnavailable` (any exception mapped to it).

[NUANCE] Tenant isolation on the status poll: a caller with a valid session for tenant A CANNOT read the readiness of tenant B's install. The route returns 404 (not 403) to avoid confirming whether the install exists.

[NUANCE] `_tenant_for_install` keys the tenant on the INSTALLATION ACCOUNT (not the repo URL). Two customers of the same public repo URL get different tenants — preventing cross-tenant `repo_maps`/`connect_readiness` sharing (P0 breach).

[NUANCE] `connect_install_start` binds the tenant to the caller's session tenant first (so connect → invite works under the same tenant), falls back to `installation_account` override, then to a random UUID (never the repo URL).

[NUANCE] `asyncio.run` on the daemon thread is safe precisely because the daemon thread has no pre-existing event loop — creating one is not a conflict.

[NUANCE] The psycopg connection is `autocommit=True` — every write is a single durable statement with no explicit transaction.

[NUANCE] The `_VALID_STATES` frozenset prevents a `'mapping'` state (which was deleted from the canonical enum) from ever being written to the DB row (belt-and-suspenders with the CHECK constraint).

[EDGE] `install_id` from an unknown/stale poll → `ConnectStore.status` returns `ReadinessReport(status="connecting")` (not an error, not a 404 — designed to not confirm existence).

[EDGE] Same repo + same account connected twice → `_tenant_for_install` returns the SAME tenant (stable UUID5) — idempotent re-connect doesn't create a second tenant.

[EDGE] Background trigger exception after the store `set_not_ready` is called → outer `_run` catches silently (already recorded).

[EDGE] `_bind_repo_row_async` with `map_store.db = None` → no-op (nothing to bind); never raises.

[EDGE] Race: two simultaneous `POST /connect/install/start` for the same repo+account → two `new_install` calls create two `connect_readiness` rows with different `install_id`s but the SAME `tenant_id` (UUID5 is deterministic). Both trigger independent pipelines. The second upsert of the `repos` row is idempotent.

## 5. `github_webhook.py` — GitHub push webhook ingress (freshness spine)

### What it does
Owns `POST /webhooks/github`: HMAC-gated (X-Hub-Signature-256 over raw body), routes verified push events to the `LivePipelineRegistry` to trigger a `WebhookHandler.handle` call and optionally a pre-meeting map refresh.

### Test items

[CAPABILITY] `POST /webhooks/github` with valid HMAC and push payload → dispatches to the registered pipeline's `webhook_handler.handle` and returns `{"status": "ok"}` at HTTP 200.

[CAPABILITY] `LivePipelineRegistry.register(repo_url, pipeline)` → normalizes URL, stores pipeline; overwrites on re-register (a re-connect rebuilds the cache).

[CAPABILITY] `LivePipelineRegistry.get_by_repo(repo_url)` → returns the registered pipeline or None; URL normalization handles `.git` suffix differences.

[CAPABILITY] `_normalize_repo_url` strips trailing `/` and `.git` suffix; case preserved.

[CAPABILITY] `_push_webhook_from_payload` → returns `_PushWebhook` for push events (has `after` + `repository`); returns None for non-push events (no `after` or no `repository`).

[CAPABILITY] `_changed_files_from_commits` → union of added/modified/removed across all commits, deduped, order-preserving.

[CAPABILITY] `_repo_url_from_payload` → prefers `clone_url`, then `html_url`, then `url`, then `ssh_url` from `repository` dict.

[CAPABILITY] `_installation_account_from_payload` → reads `installation.id` from payload, returns string or "" when absent.

[CAPABILITY] `_tenant_from_push` → derives tenant from installation account + repo URL via `connect._tenant_for_install` (same logic as connect, so push updates the right tenant's map).

[WIRING] `verify_github_signature` is called from `libs.http` over the raw body BEFORE any JSON parse — a forged/tampered body is rejected before any processing.

[WIRING] `get_pipeline_registry(app)` returns the SAME registry the connect trigger wrote to (both use `app.state.pipeline_registry`).

[WIRING] `_maybe_refresh_map` runs in a `ThreadPoolExecutor` (blocking `.result()` call) so the ingress awaits map refresh completion before returning 200.

[FAILURE] Missing/invalid `X-Hub-Signature-256` → `WebhookVerificationError` → HTTP 401, NO rebuild. safeError collapses to generic Unauthorized body (no internal leak).

[FAILURE] Non-JSON body from authenticated caller → `json.loads` raises → HTTP 400 `"invalid body"`.

[FAILURE] `payload` is not a dict → HTTP 400 `"invalid body"`.

[FAILURE] Payload is a non-push event (no `after` sha) → `_push_webhook_from_payload` returns None → HTTP 202 `{"status": "ignored"}`.

[FAILURE] No pipeline registered for the push's repo (cold instance / not connected on this host) → HTTP 202 `{"status": "accepted"}`, no rebuild triggered.

[FAILURE] `pipeline.webhook_handler.handle` raises → exception absorbed → HTTP 202 `{"status": "accepted"}` (never 500).

[FAILURE] `_maybe_refresh_map` raises → absorbed by its own `except Exception` → 200 still returned.

[FAILURE] `_github_webhook_secret()` returns "" (unset) → `verify_github_signature` must fail CLOSED (401 on every delivery) — an unverifiable delivery never triggers a rebuild.

[NUANCE] The tenant is NEVER read from the request — it is derived server-side from the signed payload's `installation.id` + `repository.clone_url`. A client cannot forge a tenant to reindex another customer's map.

[NUANCE] `signature_valid` on `_PushWebhook` is always `True` — the object is only constructed AFTER HMAC verification passes (a forged delivery never reaches this object).

[NUANCE] `_push_webhook_from_payload` reads `installation_account` from `installation.id` (B5) — the tenant-isolating identity used by `_tenant_for_install`.

[NUANCE] `_github_webhook_secret()` reads settings at REQUEST TIME (not import time) so a rotated secret is picked up without restart.

[NUANCE] `LivePipelineRegistry` is per-host in-process state (not durable): a cold Cloud Run instance has no registered pipelines — a push to a cold instance is a benign no-op (202).

[NUANCE] A force-push (`payload["forced"] == True`) sets `_PushWebhook.forced = True` — the handler should take the full-rebuild path (not an incremental delta-apply over rewritten history).

[EDGE] Same repo URL with and without `.git` suffix → `_normalize_repo_url` maps both to the same key → the registered pipeline is found regardless of suffix.

[EDGE] `changed_files` list across many commits with duplicates → deduped correctly.

[EDGE] Empty `commits` array in push payload → `_changed_files_from_commits` returns [] (not an error).

[EDGE] `repository.installation` absent (non-App delivery) → `_installation_account_from_payload` returns "" → `_tenant_from_push` returns "" → `_maybe_refresh_map` no-ops (never a cross-tenant read).

[EDGE] Pipeline registered on instance A, webhook lands on instance B (autoscaling) → instance B has no registry entry → benign 202.

[CAPABILITY] A valid bearer + known meeting + live connection → `connection.to_meeting(content, medium, to)` called; route returns `{"ok": bool, "medium": ..., "detail": ...}` at HTTP 200.

[CAPABILITY] `relay_url_for(meeting_id, base_url=<url>)` → returns `<base_url>/meetings/<id>/relay`.

[CAPABILITY] `relay_url_for(meeting_id, base_url="")` → returns `""` (honest degrade: no reachable relay).

[WIRING] `_expected_token(app, meeting_id)` traverses `app.state.meeting_runtimes → runtime.workroom.relay_token`. If any step is None, returns "" (fails CLOSED).

[WIRING] `_bearer(headers)` extracts the token from `Authorization: Bearer <token>` exactly (case-sensitive prefix, strips whitespace).

[WIRING] Route is stamped `mark_internal_scoped(meeting_relay)` so the route-enumeration test classifies it as scoped (per-meeting bearer, not a user session).

[FAILURE] Missing/wrong bearer (or empty expected token) → HTTP 401 `{"ok": false, "error": "unauthorized"}`.

[FAILURE] Non-JSON body → `request.json()` raises → HTTP 400 `{"ok": false, "error": "invalid body"}`.

[FAILURE] Body is not a dict → HTTP 400.

[FAILURE] Unknown meeting / no live runtime / no connection → HTTP 404 `{"ok": false, "error": "no live meeting"}`.

[FAILURE] `connection.to_meeting` raises → caught by `except Exception` → HTTP 200 `{"ok": false, "error": "<exc>"}` (never 500).

[NUANCE] `hmac.compare_digest` used for constant-time comparison — prevents timing attacks on the per-meeting bearer.

[NUANCE] A relay that races meeting teardown returns 404 (runtime was just removed from the registry) — the sandbox's `to_meeting` call gets an error JSON, not a crash.

[NUANCE] The route returning HTTP 200 even on a `to_meeting` failure (with `ok: false` in body) is intentional: the caller (the in-sandbox MCP server) must be able to report the failure back to the agent without getting a non-2xx that it might mishandle.

[NUANCE] `medium` defaults to `"say"` when absent or empty in the request body.

[NUANCE] `to` field: an empty string or null is normalized to `None` (no DM target).

[EDGE] `relay_url_for` with `PUBLIC_BASE_URL` from env vs explicit `base_url` parameter — the env fallback is only used when `base_url` is falsy.

## 7. `provisioner.py` — Per-meeting join spine

## Cross-subsystem integration points

These are the high-risk seams where two or more components must agree on contracts, ordering, or data shapes.

### A. Settings → All components (secrets and config)
Every component that reads a secret (HMAC keys, DB URL, API keys, signing secrets) must read from the SAME `settings` singleton that the boot gate validated. Any component that re-reads env vars directly (e.g. `os.environ.get("RECALL_API_KEY")` in `meetings.py`) bypasses the boot gate — these must be tested to confirm they agree with the validated settings values.

### B. Connect trigger → POST /meetings (cross-tenant consistency)
`_tenant_for_install(repo_url, installation_account=account)` must yield the SAME `tenant_id` whether called from `connect.py`'s `connect_install_start`, from `github_webhook._tenant_from_push`, or from the invite's session-derived tenant. If these diverge, the `repos` row is bound under one tenant but `POST /meetings` resolves the repo under a different tenant → 404. Test: connect → install_start → verify repo row tenant matches the session's tenant; GitHub push → verify same tenant as the connect.

### C. Recall webhook HMAC → drain → provisioner → MeetingRuntime
The full path: Recall pushes to `POST /webhooks/recall` → HMAC verification → durable insert → drain loop picks it up → `_dispatch_meeting_event` → `launch(payload)` → `provision_meeting` → `claim_meeting` (atomic) → `MeetingRuntimeRegistry.register`. The integration test must exercise this as a real sequence (not just unit layers): a duplicate `in_call` must not create two runtimes.

### D. Relay URL → sandbox → relay route → MeetingConnection
`relay_url_for(meeting_id)` (from `PUBLIC_BASE_URL`) is passed into `provision_workroom` (as an env in the sandbox). The sandbox's MCP server POSTs to that URL. The relay route (`POST /meetings/{id}/relay`) verifies the per-meeting `relay_token`. The token must agree between `provisioner._assemble_workroom` (where it is minted and stashed on `workroom.relay_token`) and `relay._expected_token(app, meeting_id)` (where it is resolved off `workroom.relay_token`). A mismatch → all sandbox→host communications return 401.

### E. Offer/screen/mute sinks → MeetingConnection → MeetingRuntime teardown
The `offer_sink` calls `workroom.drafts.propose_change(db, ...)` using the MAIN app's async pool. After `end_meeting` teardown, the pool is still alive but the session is gone. An offer that races teardown must not deadlock or crash the pool.

### F. Accept route → staged_drafts → objectstore (GCS)
`apply_accepted_draft` calls `objectstore.get(artifact_ref)` to load the draft body from GCS. The `artifact_ref` is a GCS path stored in `staged_drafts`. A missing or expired GCS object returns an empty string (`""`) — the notes-edit apply writes an empty patch; the code-change approve still works (the bundle_url is computed independently).

### G. Boot ordering → provisioner_ready gate → webhook drain → MeetingRuntime
The gateway route and webhook drain must NOT run before `provisioner_ready` is set (the `asyncio.Event`). If the drain starts before the registry is created, an `in_call` event could claim a meeting against an uninitialized registry. Test: verify that `provisioner_ready` appears in `BOOT_TRACE` before `routers`.

### H. GitHub push → LivePipelineRegistry → map refresh (cross-host)
`LivePipelineRegistry` is per-host in-process. A push to Cloud Run instance A when the connect trigger ran on instance B → A has no registered pipeline → 202 (benign no-op). The map refresh (`_maybe_refresh_map`) reads `app.state.map_provider` which is also per-process (wired at boot). A cold instance that receives a push before any connect trigger has run → no map refresh + no pipeline rebuild. Test: verify the 202 is returned and no error is logged.

### I. Session cookie → resolve_session → protected() → accept/reject (post-teardown)
A human clicking an accept link long after the meeting has ended relies on:
1. The `sessions` row still existing (not expired/purged)
2. The `staged_drafts` row still existing (durable)
3. `resolve_session` returning the right `tenant_id`
4. `authorize_draft_accept` matching that tenant to the draft's meeting's tenant

All four must remain consistent after the workroom teardown. The meeting's `tenant_id` comes from the `meetings` row (FK-preserved even after meeting end).

### J. Drain interval vs transcript latency
`WEBHOOK_DRAIN_INTERVAL_S = 0.25s` means each transcript line can be delayed up to 0.25s before the drain picks it up. For a fast-talking room, many lines may accumulate before each drain, but all are processed in order. The integration test for latency must use real wall-clock timing, not just ordering.

### K. Durable idempotency belt (accept/reject) vs in-flight concurrent accepts
Two `POST /m/{id}/drafts/{id}/accept` simultaneously → both hit `apply_accepted_draft` concurrently. The first transaction commits `status='applied'`; the second transaction sees the updated row and returns `already_applied=True`. Requires Postgres READ COMMITTED isolation and no TOCTOU gap between the read and the update. Must be tested under concurrent load.

### L. Meeting keep-warm vs workroom teardown
`_sandbox_keepwarm` extends sandbox lifetime every 30 minutes. `end_meeting` cancels the keepwarm task BEFORE calling `workroom.teardown()`. If the cancel races a keepwarm beat that just called `set_timeout`, the sandbox may be extended right before teardown — this is harmless. If the cancel races the `await asyncio.sleep(1800)` inside the loop, the cancel propagates cleanly. Test: verify `CancelledError` from the keepwarm task does not leak to the teardown path.

### M. Naming law: no internal names in user-visible strings
Every response body from every route must be checked by the naming lint (`lint.naming`). The routes that produce user-visible text: `GET /connect/status` (gaps/flagged_files), `POST /meetings` (error strings), `GET /m/{id}` (draft cards summary), relay responses. Specifically: no strings containing "Orchestrator", "Scribe", "workroom" (the internal component name), "code_intel", or any other internal name that CLAUDE.md lists.
